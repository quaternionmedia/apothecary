# Rust in apothecary

*Decided with the owner on 2026-10-08, one question at a time. Two pieces
are built, one is researched, and two are planned and stubbed only. Fetches
of anything new are drafted into the personal-data record (*Personal data
stays on the device*) on the governance branch before the code that makes
them lands, and a person ratifies.*

## Firmware in Rust (built)

- **The first board is the classic ESP32**: the garage's `esp32_devkitc`,
  and the ESP32 on the bench. A Rust `esp32_blink` says what the Arduino one
  says (`apothecary esp32_blink: hello` at boot and every few seconds), so
  the Machine hears it the same way. Built with `esp-hal`, flashed with
  `espflash`, on Espressif's Xtensa Rust toolchain (`espup`).
- **The toolchains are modules behind one interface.** Arduino (arduino-cli,
  esptool) and Rust for the ESP32 (cargo, espflash) are each a module that
  says what it builds, finds its tools, installs them, builds a sketch and
  flashes it. A board family or language added later -- the ESP32-C3 on
  stable Rust, AVR, the RP2040 -- is a new module, not a redesign; see the
  *Firmware toolchain seam* record, which this extends.
- **A Rust sketch lives with its part**, as an Arduino sketch does: a Cargo
  project in the part's folder, its `firmware.json` naming its toolchain.
  The Bench and a board's Machine list it beside the Arduino sketches;
  choosing it chooses its toolchain.
- **Fetched at install time only, and vendored.**
  `apothecary firmware install --rust-esp32` fetches the toolchain once into
  apothecary's tools dir and vendors each Rust sketch's crates; every build
  after that runs offline (`cargo --offline`), as an arduino-cli build does
  once its core is installed. The hosts it fetches from (the Rust
  distribution, crates.io, the GitHub releases of espup and espflash) are
  written into the personal-data record's install-time list as a draft
  before the code lands. It installs on Linux, macOS and Windows, as the
  OpenSCAD installer does; a tool named by its environment variable wins,
  then the tools dir, then `PATH`, as for arduino-cli.
- **Nothing is flashed to a real board by a test.** The suites run against
  scripted fakes of cargo and espflash, as they do of arduino-cli; flashing
  the bench's ESP32 is a step of the bench checklist.

## A Rust geometry backend (researched, not built)

Research only for now: which Rust kernel could render apothecary's scenes
(cubes, spheres, cylinders, imports, the booleans, hulls, transforms) to STL
without OpenSCAD, and how they compare by numbers.

- A write-up of the candidates -- Manifold through Rust bindings, csgrs,
  truck, Fornjot, and any other found -- with each one's licence, build
  needs, which scene operations it covers, and its maturity.
- **Test outlines for a quantitative comparison**: a corpus of scenes from
  the library and the scene models; the reference (OpenSCAD with Manifold);
  the measures (volume and surface area against the reference, bounding box,
  a distance between surfaces, watertightness, triangle count, time to
  render); written as tests that skip until a kernel is wired in, with the
  reference's numbers produced by a command, not written into prose.

## Planned and stubbed only

- **A Rust service** beside the Python server -- for example the serial and
  printer daemon, or a fast renderer the viewer talks to. A crate that
  builds and does nothing yet, and a section here saying what it is for.
- **A Rust core inside Python** (PyO3 and maturin) for hot paths: overlap
  checks, the projection, outline geometry, the finder. A crate that builds
  and does nothing yet; the wheel does not carry it.

Neither is built into the wheel or run by the suites until it does
something.

## Decided after the firmware build

Asked of the owner on 2026-10-10, after the first build of *Firmware in
Rust*, one question each:

1. **Ports: each module brings its own.** A toolchain module may find ports
   and listen to a board itself. The Rust module does, so Rust for the ESP32
   works with no arduino-cli at all; Arduino keeps `board list` and
   `monitor`. This changes the *Firmware toolchain seam* record's rule that
   only arduino-cli and esptool open a devkit's port: the amendment is drafted
   on the governance branch. The suites still open no real port.
2. **espup: fetch the archives ourselves.** espup is dropped. apothecary
   downloads and checksums the Xtensa Rust, rust-src, LLVM and GCC archives
   itself, from where Espressif publishes them, lays them out as espup would,
   and links the toolchain into the tools dir's rustup.
3. **Naming: the toolchain is always shown** -- `esp32_blink@arduino`,
   `esp32_blink@rust-esp32` -- everywhere a sketch is named: the Bench, the
   Machine, the CLI, build ids and messages. A node that expects `esp32_blink`
   matches a board running either build, and the Machine says which
   toolchain's build it is. The hello the board prints stays as it is.
4. **The Install cell becomes a ring.** Panels › Bench › Install opens a ring
   of the toolchain modules -- Arduino's, Rust for the ESP32, and each later
   module, drawn from the registry -- so every module's install has an
   address, and today's Install address moves one level deeper.
5. **Pins: by hand, and no licence gate yet.** A pinned version moves only in
   a commit that bumps it, and that commit re-runs the real install and the
   offline build and says the result in its body. No cargo licence gate for
   now.
6. **Install flags: only what is asked.** Each flag installs its own module
   and nothing else; `apothecary check` and the Bench say which modules are
   installed and what each can do.

Two more, found while building and needing no question: no absolute build
path -- and so no user name -- is in a flashed image; and the Arduino
`esp32_blink` says what it does, a hello every ten blinks.
